# 마지막 접근의 기체·차량 속도오차 예산

v23의 목표속도 피드백 수식 수정은228시험을 통과했지만 착지 정확도를 개선하지 못했다. 재사용 조건571/619의 동시 접근 후보는 기존 단계 정책보다 접촉 오차가 각각18.50/17.01mm 커져 사전+10mm 기준을 실패했다. 두 정책의 네 조건부 접촉은 별도 물리 로그로 보존하며 후보는 채택하지 않는다. v23의 실제 독립 검토final/index(11:00:07KST)를 읽고main에서원908파일·이전112판정·226검토근거의SHA와네조건부접촉서명을결합했다. 후보 채택 거절은 유지한다. qualified/formal/실기 성공은0이다.

다음 수정의 근거를 확보하려고 v23네 경로와 v22동시 접근 두 경로를 사후 분석했다. 새 비행이 아니며 전체 완료 원장177을 증가시키지 않는다. [분석 코드](../../scripts/analyze_mission3_terminal_imu_budget.py), [접촉 전 결과](../../artifacts/mission3/acquisition/20261009-terminal-imu-budget-precontact-v2/summary.json), [복사된 원 분석 코드](../../artifacts/mission3/acquisition/20261009-terminal-imu-budget-precontact-v2/analyze_mission3_terminal_imu_budget.py)를 함께 보존한다. 첫 접촉 시각까지 포함한 v1은 충격 표본이 섞일 수 있어 보존하고, v2는 최초 접촉 전의 마지막50Hz truth 표본까지만 계산했다. 해당 구간의 접촉 표본은 전 경로0이다.

센서 기록은100Hz이고 actual 위치·속도·자세 기록은50Hz다. 같은 시각 사이의 actual 속도/자세를 사후 보간했다. 각 sensor 업데이트의 기체 추정 속도 증분을 기록된 IMU 예측, 기존 바닥 잔차 차감, 추가 융합으로 나눴다. 전 여섯 말기 구간에서 Flow융합0·추가 수평 속도 보정0이며 속도 증분 예산의 수치 잔차는1e−10m/s 미만이다. 이것은 기록된 알고리즘의 계산 결합 검사이며 센서가 정확하다는 증거는 아니다.

상대 위치오차를 `추정 패드−추정 기체−(actual 패드−actual 기체)`로 정의하면, 영상 보정이 없는 구간의 변화는 차량 속도오차 적분에서 기체 속도오차 적분을 뺀 값이다. 접촉 전 여섯 경로의 이 관계 잔차는 최대.095mm다. 서로 종속된 폐루프 항을 독립적인 원인 비율로 더하지 않는다.

이 변화량은 첫 접촉의 실제 착지오차와 같은 값이 아니다. 기체의 위치·속도 추정이 드리프트하면 제어기가 작은 추정 오차를 보더라도 실제 패드 중심과 어긋날 수 있다. v23동시571은 말기 시작부터 기체 횡방향 속도오차+4.704mm/s가 있었고 접촉 직전+10.671mm/s였다.619는−6.925→−15.062mm/s였다. 따라서 차량 FF만 일정량 바꾸는 방법은 근거가 부족하다.

그림의 회전 대입은 기록된 평균 body 가속도를 사후 actual 자세로 돌려본 민감도다. body 가속도는 이전1kHz IMU 창의 평균인데 actual 자세는 현재50Hz 보간값이므로 같은 시간 평균 자세가 아니다. 이 항에는 heading 정렬도 포함된다. 잔여 항은 평균·잡음·동역학·시각 근사의 혼합이다. 회전과 기존 바닥 잔차 차감의 상쇄가 후보별로 달라지지만 이를 유일한 중력보정/가속도 칩 편향의 원인으로 확정하지 않는다. 실기 timestamp·노출/전송·IMU 수신 및 동역학 검증은 여전히U다.

후속 설계는 두 종류로 나눠 검토한다. 하나는 기체 자세·중력보정·잔차 전파를 정확한 sensor 창 시각으로 재생하는 방법이다. 다른 하나는 마지막 유효 영상이 있을 때 상대 위치·상대 속도·수평 IMU 잔차를 함께 추정해 영상 소실 직전의 상태를 개선하는 방법이다. 카메라 상대 위치만으로 기체와 차량의 공통 속도나 자세/칩 편향을 모두 분리할 수 있다고 가정하지 않는다. 확인된 직선에서 일정 차량 속도라는 과정 가정을 사용한다면S로 명시하고, 기존 바닥 Flow의 기준·상태 간 상관·불확실성을 보존해야 한다. 현재 live 추정기에 이 두 방법을 새로 연결하지 않았다.

[Bitcraze 공식 상태 추정 문서](https://www.bitcraze.io/documentation/repository/crazyflie-firmware/master/functional-areas/sensor-to-control/state_estimators/)는 Flowdeck의 ToF와 optical flow를 함께 속도 측정 모델로 사용한다고 설명한다. 실제 현재 프로필은 공식 onboard EKF와 별도 PC100Hz IMU/표면 observer를 사용하므로 이 웹 설명만으로 PC 구현의 일치나 성능을 승인할 수 없다. 현재 검토 근거는 각 run의 고정 source/runtime snapshot이다. 접근일2026-10-09, 공식 문서의 현재 master 설명C와 설치 고정 코드를 구분한다.

[Lee 등2020 논문](https://arxiv.org/abs/2008.05699v3)은 착륙면에 수직인 시각 표식과 단안 카메라로 상대 거리·heading을 추정하는 접근을 보고한다. 우리 rear-facing 수직판의 연구 방향과 관련되지만 표식·렌즈·기체·제어·검증 조건이 다르다. 여기서는 초록과 메타데이터만 읽었으며 해당 논문의 정확도나 실기 성공을 이 시스템에 옮기지 않는다.

[Bouazza 등2026 개정 논문](https://arxiv.org/abs/2512.19245v2)은 양쪽 시스템의IMU와 통신, 단안 영상, 지속적 자극 조건으로 상대 상태 observer를 구성한다. 우리에게는 차량IMU/통신이 제공되지 않으므로 그 관측 가능성·수렴 결과를 직접 적용할 수 없다. 초록만 확인했으며 해당 입력을 숨겨서 추가하지 않는다. 상대 상태를 먼저 설계하되 필요한 센서/운동 조건을 검사한다는 연구 방향만 참고한다.
