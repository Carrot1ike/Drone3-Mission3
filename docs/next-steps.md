## 첨부 자료에 따른 우선순위 보완

9월 18일 경기규정(안) 11장과 계획서 가이드의 `2. 기술개발계획서 양식!A2`는 **예선에서 시뮬레이션 시연·결과 제출을 필수로 요구하지 않는다**고 명시한다. 기체는 본선 진출팀에 지급한다. 따라서 장비 지급을 위해 물리 착륙 시뮬레이션을 먼저 완성해야 한다는 전제로 일정을 잡지 않는다. 현재 관측 시험은 설계·검증 계획을 뒷받침하는 근거로 활용한다.

PC 연산 허용 범위와 Flow deck 지급 여부는 아직 확정 안내 대상이다. PC + Flow 경로는 조건부 개발 구성으로 표시하고, 영상·관측·제어·명령 전송 인터페이스를 분리한다. 온보드로 옮기는 대안은 AI-deck 연산·전송 자원과 제어 주기를 확인한 별도 구현 검토가 필요하며 단순 실행 위치 변경으로 완료됐다고 쓰지 않는다.

대회는 표식·경로, 장애물 회피, 이동 차량 착륙의 연속 미션이다. 착륙 개발은 유지하되 예선용 전체 시스템도·미션 전이도에는 1·2단계를 포함한다. 자료의 정확한 위치·점수·미확정 사항은 [대회 자료 대조](competition-requirements.md)에 기록했다.

## 먼저 해결할 관측 문제

현재 `aruco_pose.py`는 복수 PnP 후보를 정밀화한 뒤 재투영 오차가 가장 작은 해 하나를 반환한다. 프레임 간 이력과 신뢰도는 없다. 기존 결과에서 아래 사례를 확인했다.

| 기존 보고서의 t = 1.55 s 샘플 | 값 |
| --- | --- |
| 마커 중심의 병진 추정 오차 | 약 1.25 cm |
| 마커 자세의 회전 오차 | 약 19.73° |
| 마커→착륙점 변환 후 위치 오차 | 약 14.59 cm |
| 영상 재투영 RMSE | 약 0.121 px |
| 마커의 가장 짧은 영상 변 | 약 21.06 px |

착륙점은 마커 중심과 다른 점이다. `p_pad^C = t_marker^C + R_marker^C · r_pad^M`이므로 회전 추정 오차도 착륙점 위치에 전달된다. 현재 실험 오프셋 길이는 약 42.72 cm이다. 회전 오차 θ에 따른 오프셋 변환 오차의 상한 `2 · |r| · sin(θ/2)`은 이 샘플에서 약 14.64 cm이다. 이 상한은 실제 오차 전체가 회전 때문에 생겼다는 증명은 아니지만, 낮은 재투영 오차만으로 착륙점을 신뢰할 수 없음을 보여준다.

수치는 기존 [JSON](../artifacts/landing-visibility.json)과 해당 시각의 장면 기하를 평가용으로 대조해 계산했다. 참값은 관측기나 제어기 입력으로 제공하지 않는다. 평면 PnP의 복수 해와 LM 재투영 정밀화는 [OpenCV 공식 문서](https://docs.opencv.org/4.13.0/d5/d1f/calib3d_solvePnP.html)를 따른다. 단순 평활화는 잘못 선택한 자세나 체계적 오차를 해결한다고 가정하지 않는다.

### A1: 영상 관측기부터

기존 검출 함수를 유지하거나 호환 wrapper를 두고 후보 목록을 반환하는 경로를 추가한다. 프레임 식별자, 촬영 시각의 존재 여부, PC 수신 시각, 좌표 프레임, 마커 크기/보정 프로파일, 각 후보의 회전·병진·재투영 오차·모서리 크기를 함께 전달한다. 수신 시각으로 알 수 없는 촬영 지연을 0으로 채우지 않는다.

선택·추적 블록은 후보 간 차이, 시간 일관성, 지연·누락·순서 역전과 추정 근거를 기록한다. 신뢰할 수 없는 관측을 마지막 pose로 조용히 대체하지 않는다. 모호한 회전에서 착륙점 위치의 불확실성이 커지는 효과를 반영한다. 카메라가 회전하는 상황의 상대 위치 단순 차분을 차량 world 속도로 사용하지 않는다.

관측 평가에서는 선택한 관측의 오차와 유효 판정 비율을 함께 보고한다. 모든 관측을 버려 오차만 작게 보이는 방법도, 모든 검출을 믿어 큰 오차를 숨기는 방법도 통과로 간주하지 않는다. 현재 명목 경로의 검출·근접 4 cm 기하 기준은 기존 회귀 검사로 유지하고, 새로운 관측기의 단계별 기준은 실행 전에 별도로 고정한다. 실패한 조건을 제외하거나 기준을 완화해 완료 처리하지 않는다.

### A2: 제어 명령이 카메라 경로를 만드는 시험

첫 목표는 **정지 착륙장을 향한 정렬과 접근**이다. 상태기계는 목표·단계를 고르고, 외부 제어기는 오차로부터 속도·yaw 보정을 계산한다. 정상 관측, 모호성, 짧은 손실, 지속 손실 상태를 분리한다. 신뢰도 부족 시 접근을 제한하고 명시적인 회복/중단 분기로 들어간다.

렌더 → 관측 → 목표/상태기계 → 제어 명령 → 카메라 운동 → 다음 렌더의 순환을 만든다. 현재 `preview_landing.py`의 직접 지정 경로를 제어기 출력인 것처럼 재사용하지 않는다. 이 시험대에서 가정한 이상적 자세·명령 추종이나 지연은 실험 입력 계약에 표시한다. `T_BC` 없이 카메라 중심의 명령을 실기 CFLib body/world 명령으로 변환하지 않는다.

평가 항목은 시간에 따른 정렬/접근 오차, 관측 유효율, 목표 도달 시간, 명령 포화, 손실 시 단계 전환과 회복이다. 하강 명령과 접촉 성공은 첫 시험의 범위에서 제외한다. 목표 도달 여부는 평가 참값으로 검사할 수 있지만 제어 단계 전환은 관측·추정값으로 결정한다.

### B1: 이동 표면 Flow/ToF를 독립 시험

차량과 관측 센서가 같은 0.3 m/s로 이동하면 표면 대비 병진 속도는 0이다. 기존 CrazySim Flow 계산은 관측 표면의 이동을 빼지 않으므로 이 경우를 별도 검사한다. 바닥→20 cm 높이 상판 전환, 깃발/지지대의 광선 검출, 표면 종류·거리·상대속도를 함께 기록한다. 모델 출력의 단위와 부호, 회전 성분은 순수 병진 사례와 분리한다.

센서 벤치는 동역학 없는 지정 운동으로 만들 수 있으므로 기체 관성·추력 자료를 기다릴 필요가 없다. 센서 장착 원점·방향 미확정은 실험 가정으로 기록하고 실제 Flow deck 성능으로 표현하지 않는다. 차량 참값 속도를 벤치의 기대값 계산에 쓰는 것과 실기 추정기에 공급하는 것을 구분한다.

현재 가시성 장면의 mocap 차량을 그대로 접촉·마찰 착륙 플랜트로 사용하지 않는다. MuJoCo는 mocap 물체를 물리 모델에서 고정된 것으로 취급해 접촉 상대속도 성분을 반영하지 않는다. 물리 검증에 들어갈 때는 차량의 실제 표면 속도와 접촉 상대속도가 엔진에 반영되는 모델을 확인해야 한다. [MuJoCo 3.14 공식 문서](https://mujoco.readthedocs.io/en/3.14.0/modeling.html#mocap-bodies).

## 실행·비교·완료 범위

관측, 제어, 명령 제한, 전송 adapter, 평가 참값을 분리한다. 실행마다 코드/설정/의존성 버전, 입력 허용 목록, seed, 지연·손실 조건과 참값 주입 여부를 기록한다. 미래 RL 비교에서도 FF + 피드백과 같은 관측·목표·안전 계층·최종 명령 형식을 사용한다. 먼저 FF + 피드백 기준선을 확보한 뒤 RL을 추가한다.

기체 사양 제한은 그대로 유지한다. 제조사 미공개 관성·추력 항목을 제3자 모델 값으로 대체하지 않으며, 해당 값이 필요한 기체 동역학·물리 접촉 검증은 근거가 확보될 때 착수한다. 지금 완료할 수 있는 관측·운동학·센서 시험과 예선 설계 문서는 계속 진행할 수 있다.
